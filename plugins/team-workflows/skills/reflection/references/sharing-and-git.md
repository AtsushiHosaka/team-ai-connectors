# ふりかえりの共有とGitの手順

## ユーザー用設定

`schema_version: 1`の個人設定から、本人の`nickname`と`projects`内の今回のプロジェクトだけを使います。GitHubのリポジトリでは、実際のremoteから確かめた`ホスト名/owner/repo`をプロジェクトのキーにします。SSHとHTTPSの違いをそろえ、末尾の`.git`と認証情報を除きます。GitHub Enterpriseでは実際のホスト名を含め、同名の別リポジトリと区別します。それ以外はプロジェクトディレクトリの絶対パスを使います。設定のキーと作業場所を照合し、別のプロジェクトの設定を既定値として使いません。

| 項目 | 用途 |
|---|---|
| `nickname` | ふりかえり本文に書く本人のあだ名 |
| `projects[今回のキー].slack.workspace` | 接続先を確認するためのワークスペース |
| `projects[今回のキー].slack.channel_id` | 投稿先のチャンネルID |
| `projects[今回のキー].slack.channel_name` | 投稿前に表示するチャンネル名 |
| `projects[今回のキー].slack.post_mode` | `confirm`は本文を確認して投稿、`auto`は許可された内容を投稿、`off`は投稿しない |
| `projects[今回のキー].github.push_mode` | `ask`は実行前に確認、`auto`は許可された今回の変更をcommit・push、`off`は実行しない |
| `projects[今回のキー].github.remote` | pushするremoteの名前。実際のURLが今回のリポジトリを指すことも確認する |
| `projects[今回のキー].github.branch` | 自動pushを許可されたブランチ名 |

macOS・Linuxでは`~/.config/team-ai-connectors/profile.json`、Windowsでは`%APPDATA%/team-ai-connectors/profile.json`を読みます。設定がない場合や未対応の形式の場合は、勝手に上書きせず`setup`を案内します。保存時は他の`projects`の設定を残します。ブラウザ版AIなど端末のファイルにアクセスできない場合は、会話で分かる設定を今回だけ使います。

`auto`は、本人が用途と共有範囲を理解して選んだときだけ使います。今回のプロジェクトと一致しなければ適用しません。Gitのremote・ブランチが設定と違う場合も、変更前に確認します。「今回は投稿しない」「pushだけして」といった今回の指示を優先します。今回だけ指定された投稿先で、保存済みの既定値を勝手に書き換えません。

## Slackの接続と投稿

1. クライアントで使える公式Slackプラグイン・コネクタのツールを調べます。接続状況と権限を確かめ、同じSlackを別の方法で重複設定しません。認証が必要なら公式の接続画面を案内し、トークンをチャットへ貼るよう求めません。
2. 今回のプロジェクトに設定したワークスペースとチャンネルIDを、ツールから得た情報と照合します。名前が一致する別ワークスペースへ送らないようにします。ユーザーが名前だけを伝えた場合は検索・情報取得でIDを確かめ、候補が複数あればユーザーに選んでもらいます。利用可能なツールで接続先を確かめられない場合は、その点を質問します。
3. チャンネルが閲覧・投稿可能か確かめます。非公開チャンネルや権限エラーを回避するために、別のチャンネルへ変更したり、勝手に参加したりしません。ユーザーが指定したスレッドがある場合だけ、そのスレッドへ返信します。
4. 最終下書きに、本人のあだ名と今回の作業を入れます。あだ名は本文の署名に使い、Slack上の別ユーザーになりすましません。根拠のURLは共有相手がアクセスできる範囲を確かめ、環境変数、認証情報、端末の個人情報を除きます。
5. `confirm`で投稿の許可がまだなければ、投稿先と本文を一度示します。ユーザーが今回の完成した本文の投稿を指示済みなら、その指示で進めます。`auto`は本人が許可した作業報告の範囲に限ります。機微な評価内容や新しい宛先まで自動投稿の範囲を広げません。
6. 投稿ツールへ確定したチャンネルIDと本文を渡します。成功応答のチャンネルID・メッセージIDを確認します。利用できる場合は投稿URLの取得や読み戻しで確認し、URLを返します。投稿成功は確認できてもURLが取れない場合は、その違いを伝えます。
7. タイムアウトなどで結果が不明なら、同じチャンネルの投稿結果を調べます。送信済みか確かめられないまま再投稿しません。「投稿は未確認」と報告し、下書きを保持します。

投稿する本文は次の形を目安にします。分からない項目は作らず、短い回では項目を減らします。

```text
ふりかえり｜あだ名｜対象の作業

今日できたこと
取り組んだことと、実際に確認できた結果。

判断と学び
本人が決めたこと、AIに任せたこと、確認・修正したこと。

次回試すこと
本人が選んだ行動と、改善したかを確かめる方法。

根拠と未確認事項
成果物・テスト・commitやPRのURLと、まだ確かめていない点。
```

## GitHubへのcommitとpush

Gitの操作はSlackへの投稿と別に判断します。pushしなくても振り返りの下書きは作れます。pushに失敗しても「未push」と明記して、許可されたSlackへの報告は続けます。

1. 今回の作業リポジトリを確認します。`git status --short --branch`、現在のブランチ、remote、upstream、作業ツリー・ステージ済み差分、未追跡ファイルを調べます。表示・共有するremoteのURLに認証情報が含まれていないか確かめます。
2. 今回の本人とAIの作業範囲を差分に対応させます。既存のステージ済み変更も無条件に今回の変更とみなしません。誰の何の変更か分からなければ、その範囲だけを確認します。個人設定、秘密情報、無関係な生成物を含めません。
3. `ask`では対象のブランチ・remoteと変更の要約を示し、commit・pushするか聞きます。既存の明示的な許可や、プロジェクト・remote・ブランチが一致する`auto`があれば進めます。不一致なら、設定の変更や今回だけの実行を確認してから進めます。pushだけを許可された場合は、未commitの変更を勝手にcommitしません。`auto`の設定時には「このプロジェクトの指定ブランチで、今回の自分の変更をcommitして通常のpushを行う」という範囲への同意が必要です。
4. 対象が決まったら必要なチェックを行います。すでに同じ内容で終えたチェックは再実行せず、その結果を使います。未検証ならその事実を記録し、成功したことにしません。今回のファイルやhunkだけを明示してステージし、差分をもう一度確認して内容を表すcommitを作ります。`git add .`で無関係な変更までまとめません。
5. リモートの状態を取得し、upstreamに対するahead・behindと、pushで送られる全commitを確認します。範囲外の作業や他人の未pushのcommitが混ざる場合は、そのまま送らず確認します。behindや分岐があれば、勝手なrebase・merge・force pushで解決せず、状況と選択肢を伝えます。upstreamがない場合は既存のブランチとremoteを確認し、行き先が確定してから通常のpushを行います。別のremoteや新しいブランチを推測で作りません。
6. 通常のpush後に終了結果を確認し、可能ならリモートのブランチ先端が対象commitを指すことも確認します。commitのSHAとGitHubのURLを控えます。ローカルcommitができただけで「GitHubに保存した」と報告しません。
7. 最後に作業ツリーとahead・behindを確認します。残った変更、未pushのcommit、実行できなかったチェックを伝えます。他の作業の変更を消したり、勝手にstashしたりしません。PRの作成・マージやデプロイは、別途その操作が依頼されている場合だけ行います。

GitHubへアクセスできないAIでは、対応していない操作を実行済みとせず、必要な操作と現在の状態を返します。GitHubプラグインを使う場合も、今回の対象、commit・pushの許可、リモート結果の確認は同じです。
